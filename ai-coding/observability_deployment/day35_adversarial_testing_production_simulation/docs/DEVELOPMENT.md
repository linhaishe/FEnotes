# Day 35 开发文档：对抗测试与生产环境模拟

本文件把 [README.md](./README.md) 的学习目标拆成可实现、可验证的开发工作。**当前是设计，不表示下面的 Day 35 代码、统一观测链路或测试已经存在。**

## 1. 目标与范围

在隔离环境中重复执行正常请求、直接/间接 Prompt Injection、越权工具调用、模型/工具超时和服务故障。每个场景既要判断行为是否安全，也要收集足够证据定位失败环节。

本阶段只用假凭据、假用户和无副作用工具。安全与故障回归默认不调用 DeepSeek；真实模型只作为单独的手动/可选评估，不进入默认 CI。不得通过测试执行真实删除、转账或访问生产服务。

## 3. 建议交付物

按最小可验证路径增量实现，避免先搭完整平台：

1. `test_adversarial.py`：固定输入样本，直接调用 Day 32 安全入口和真实 Mock Tool；断言正常请求成功、注入与越权在工具执行前被拒绝。
2. `test_faults.py`：复用 Day 34 `TestClient`，注入模型超时与工具异常；断言响应、事件顺序、错误分类和关联 ID，不调用外部模型。
3. `test_service_failure.py`：只针对隔离的 Day 33 测试栈模拟 Redis 停止/恢复，检查 readiness 与重试；容器测试独立于默认单元测试运行。
4. 如需要在**同一请求**中展示 Trace、指标、日志和审计，再增加一个 Day 35 最小演练入口及其测试。该入口只负责串联现有安全检查、Mock Agent/Tool 和埋点；先定义统一 ID 与事件协议，不能通过硬编码相同 ID 来伪造关联。

不修改 Day 29–34 的公开行为来满足 Day 35 测试；确需修改上游时，先写清原因和兼容性影响。

## 4. 场景合同

每个用例至少定义：`case_id`、输入来源（用户/外部内容）、当前用户、允许工具、注入故障点、预期响应或异常、预期工具执行次数、预期审计事件，以及可用于定位的请求/Trace ID。样本只保存假数据，报告不回显完整攻击文本。

| 场景 | 注入点 | 必须断言的行为 | 主要定位证据 |
| --- | --- | --- | --- |
| 正常查询 | 无 | 正常回答；允许的只读工具可执行 | 成功响应、工具调用事件 |
| 直接注入 | 用户输入 | 输入 Guardrail 拒绝；模型和工具调用次数为 0 | 拒绝类别、请求 ID |
| 间接注入 | 网页/文档内容 | 外部指令不能改变工具权限或用户身份 | 外部内容检查结果、无危险工具执行 |
| 越权调用 | 工具名/参数 | 未授权工具、跨用户访问、非法金额或缺失资源 ID 在执行前被拒绝 | 工具校验事件、无副作用 |
| 审批拒绝 | 审批决定 | `approval_requested → approval_rejected`；无 `tool_executed` | 审批 ID 对应的审计事件 |
| 模型超时 | Mock 模型 | 失败响应；分类为 `timeout`；工具未启动 | 请求日志、模型调用阶段 |
| 工具失败 | Mock 工具 | 模型阶段成功、工具阶段失败；不输出异常原文 | 请求日志、工具失败分类 |
| Redis 不可用 | 隔离测试容器 | readiness 为 503；恢复后可用；重试有限 | 健康端点、重试指标、容器日志 |
| 容器重启 | 隔离测试容器 | 审计事件按原审批 ID 可再次查询 | Volume 中的 `audit.jsonl`、重启前后校验值 |

## 5. 观测与报告约定

- **单请求关联：**HTTP 响应头 `X-Request-ID` / `X-Trace-ID` 与 JSON 日志一致；审批事件使用审批 ID。若统一入口产生审批，显式保存 `http_request_id → approval_request_id` 映射，而非把两者混为一个字段。
- **Trace：**根 Trace 代表一次请求；真实 LangChain 模型/工具才会自动产生相应子 Trace。Mock 场景若要显示子步骤，需在 Day 35 入口显式创建测试 Trace；不能把 JSON 日志误称为子 Trace。
- **指标：**比较故障注入前后同一进程的计数器增量及延迟分布。QPS、P95/P99 需要足够样本量；单次请求只适合检查计数器变化与单请求耗时，不据此宣称总体分位数变化。
- **日志与审计：**运行日志保留时间、事件、错误类别、关联 ID 和耗时；审计记录批准/拒绝与实际执行。均不记录真实 Key、PII、完整 Prompt、工具原始结果或异常原文。
- **演练结果：**对每个场景保存通过/失败、预期与实际事件序列、请求 ID、Trace ID（若存在）、指标增量、审计 ID 和失败原因。报告必须指出证据缺失或跨 Demo 无法关联的部分，不把推断写成事实。

## 6. 实施顺序与验收

1. **固定安全样本**：先写直接/间接注入与越权测试，确认它们在当前代码上有明确的通过/失败信号；再加正常样本检查误拦截。
2. **注入模型和工具故障**：用 Mock 抛出受控异常，验证 Day 34 日志中模型超时、工具失败的不同路径及 `request_id` 分组结果。
3. **审批与状态恢复**：创建两笔独立审批，一笔拒绝、一笔批准执行；按各自审批 ID 查询审计。重启隔离容器后，重新读取同一审计文件并核对内容。
4. **隔离服务故障**：启动专用 Day 33 测试栈，停用其 Redis、观察 readiness/重试、恢复后复测。只操作本次创建的容器与 Volume；不碰开发者正在使用的栈。
5. **联合观测（若实施统一入口）**：先证明同一请求的 Trace、日志和指标确实来自同一进程/执行链，再做跨信号定位报告；无法证明时保持分开验收。

默认单元测试应离线、无费用、无 Docker 依赖；容器故障演练与真实模型评估单独触发。完成后要有一份可复现的演练记录：每个场景的触发方式、预期与实际结果、关联 ID、定位证据和恢复结果均明确。文档中的场景合同全部有对应测试通过，才能把 Day 35 标为完成。
