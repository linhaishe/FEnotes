# Day 39：Fine-tuning 决策与数据

本日目标：先用评估证明模型存在**可训练的能力缺口**，再准备去重、隔离、可追溯的训练/验证/测试集，以及可验证的工具调用轨迹。今天不训练模型；Day 40–41 才做 SFT 与 LoRA/QLoRA 实验。

- Day 39：先评估是否需要微调，准备和隔离数据。
- Day 40–41：在条件具备时做 SFT + LoRA/QLoRA，并与基线比较。
- Day 42：理解 DPO、RFT/GRPO 等进一步训练方法，重点设计评估、灰度发布和回滚。
核心顺序是：先证明有能力缺口 → 再训练 → 用保留集证明收益 → 决定是否发布。如果 Day 39 的评估表明 Prompt、RAG 或工具流程已能解决问题，后面可以得出“不微调”的结论。

微调的内容是不是可以让算法组去处理？

可以，而且通常更合理。训练实现——数据处理流水线、SFT/LoRA/QLoRA、超参数、显存优化——可以由算法组负责；但你作为 Agent 应用方，最好不要把微调需求整个“扔过去”。
你需要提供并共同确认的是：具体要解决哪些失败样本、未微调基线、训练/验证/测试集的隔离规则，以及最终答案、工具选择和安全性的验收指标。算法组交付模型或 Adapter 后，你再负责接入、同题评估、灰度和回滚。

## 二、核心知识总结

### 什么时候不该微调

先把错误归因，而不是把所有低分都叫“模型能力不足”：

| 失败原因 | 优先尝试 |
| --- | --- |
| 指令不清、输出格式不稳定 | 明确 Prompt、少量示例、结构化输出与校验 |
| 缺少最新或私有事实 | RAG、数据库或只读工具；训练不适合记住持续变化的事实 |
| 工具参数、权限或流程设计错误 | 修工具 Schema、参数校验、审批与 Agent Harness |
| 固定任务经上述改进后仍反复失败，且有足够高质量标注 | 才考虑 SFT/LoRA，并与未微调基线比较 |

微调决策必须回答：失败样本有多少、集中在哪类任务、现有方案改进到什么程度、预期收益是否值得训练/维护成本；无法给出可重复的保留集指标时，结论应是**暂不微调**。

### 数据集的三个角色

- **训练集（train）**：用于更新模型权重，可在训练阶段反复查看和清洗。
- **验证集（validation）**：用于选超参数、比较训练轮次、早停；调参过程中会间接“看见”它。
- **测试集（test）**：最终一次性评估，固定并封存；不能据其错误反复改 Prompt、改数据或选模型，否则它就不再是独立测试集。若需要迭代，请另建新的保留集。

先去重再切分。相同/近似 Prompt、同一订单的多轮对话、同一模板替换名字或金额后的样本，应按 `conversation_id`、`order_id` 或模板家族分组进入同一分区。记录划分种子、规则和数据版本；再检查跨集近重复、标签分布和边界/攻击样本覆盖。清除密钥、PII、系统提示词和不具备训练授权的内容。

### 工具调用轨迹是什么

工具轨迹不仅是最终答案，还要记录模型选择的工具、参数、工具返回、后续决策与最终结果。最小示例（全为虚构数据）：

```json
{
  "case_id": "refund-001",
  "input": "查询订单 order-1 是否可退款",
  "expected_tool_calls": [
    {"name": "mock_order", "arguments": {"order_id": "order-1"}},
    {"name": "mock_refund_rules", "arguments": {"rule_id": "standard"}}
  ],
  "tool_results": ["已支付", "符合退款规则"],
  "expected_outcome": "可退款，执行前仍需审批"
}
```

这个结构是**评估/数据设计示意**，并非可直接上传给某个平台的训练格式。后续要按所选模型的 chat template、工具调用格式转换；工具结果是环境反馈，不能把未经核实的模型自述当作成功工具调用。轨迹里也应保留“不应调用写工具”“参数错误应被拒绝”等负样本，避免模型只学会过度调用工具。

## 三、Task / Project 学习路线

沿用 Day 36–38 的假订单与退款规则，选一个窄任务：**根据订单事实与规则，生成结构化退款结论并选择只读工具**。今天只做决策与数据，不接真实支付工具。

### Task 1：冻结评估口径与未微调基线

- 固定样本、模型版本、Prompt、工具权限和评分器；运行未微调基线。
- 分开统计最终结论正确率、JSON/Schema 合法率、工具选择准确率、参数准确率和危险写工具误调用率；同时记录 Token、延迟和成本。
- **产出/验收**：逐样本结果与汇总表，能复现每类失败，而不是只报告一个总分。

### Task 2：诊断缺口，做微调 Go/No-Go 决策

- 将失败样本分成 Prompt、知识/RAG、工具/流程、模型能力与标注不确定五类。
- 对主要失败类别先试简单修复，并在同一评估口径下复测；写出“为何仍需要/不需要微调”。
- **产出/验收**：一页决策记录，包含剩余缺口、预期改善指标、成本与暂不微调的条件。若简单方案已达标，则停止训练准备。

### Task 3：定义样本 Schema 与标注规范

- 定义 `case_id`、场景/来源、用户输入、可用工具、期望工具与参数、工具结果、期望结论、风险标签和分组键。
- 明确多解情况、拒绝样本与需人工复核样本；禁止把未经审批的退款执行标成正确动作。
- **产出/验收**：字段说明和少量人工复核样例；同一输入由两人标注时争议可被记录并解决。

### Task 4：清洗、去重与安全检查

- 去除重复 ID、完全重复与近重复样本；按订单/对话/模板家族分组，阻止跨集泄漏。
- 扫描并移除密钥、PII、真实用户数据、完整内部 Prompt；记录来源、授权和清洗规则。
- **产出/验收**：去重前后数量、被排除原因、抽检结果；敏感数据扫描通过。

### Task 5：划分并冻结 train / validation / test

- 先按分组键切分，再检查各分区的场景、难度和风险标签覆盖；保留真正未见过的订单/模板家族作为测试集。
- 将划分种子、输入数据版本、分区清单与哈希记录下来。测试集只用于最终对比，不参与调参或补训练数据。
- **产出/验收**：三个互斥分区，跨集重复/同组泄漏数为 0，且每个分区可追溯到来源。

### Task 6：整理工具轨迹并交接 Day 40–41

- 核对每条轨迹的工具名、参数、调用顺序、Mock 工具返回和最终答案；失败轨迹按“错误示例”标注，不直接当作正向 SFT 标签。
- 依据后续训练工具链转换训练格式，保留原始规范样本与转换脚本/规则；在验证集检查格式与标签，在封存测试集上只做最终比较。
- **产出/验收**：可复现的数据版本、轨迹质检报告、数据卡和未微调基线；Day 40–41 能使用同一评分口径比较训练后结果。

## 四、完成标准

- 有明确的微调 Go/No-Go 结论，并有评估数据支持；“不微调”也是合格结果。
- 训练、验证、测试三集去重且按业务实体/模板家族隔离，测试集未参与开发迭代。
- 工具调用轨迹含选择、参数、结果与最终结论，正负样本边界清楚。
- 数据来源、授权、清洗、版本和安全检查可追溯；无凭据或 PII 进入训练材料。
- 未微调基线与后续训练使用相同测试口径，能比较质量、延迟、Token 和成本。
