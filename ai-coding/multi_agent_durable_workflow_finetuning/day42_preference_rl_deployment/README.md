# Day 42：偏好/强化微调与部署

本日目标：理解 DPO、RFT/GRPO、Grader 与 Reward Hacking 的适用边界；基于 Day 39–41 的基线和候选模型，设计**可验证、可灰度、可回滚**的发布方案。本目录目前是学习大纲与知识总结，不代表已执行训练或生产发布。若先前评估不支持进一步训练，完成“为什么不训练”的决策记录同样合格。

## 一、阅读顺序

1. [TRL 总览](https://huggingface.co/docs/trl/index)：先认清 `SFTTrainer`、`DPOTrainer`、`GRPOTrainer` 的任务差异。
2. [TRL DPO Trainer](https://huggingface.co/docs/trl/dpo_trainer)：看 `prompt` / `chosen` / `rejected` 偏好数据及参考模型的作用。
3. [TRL GRPO Trainer](https://huggingface.co/docs/trl/grpo_trainer)：看采样、奖励函数、组内比较和训练指标。
4. [OpenAI Fine-tuning API 参考](https://developers.openai.com/api/reference/resources/fine_tuning)、[Model optimization](https://developers.openai.com/api/docs/guides/model-optimization)：理解托管训练任务与评估闭环。**平台可用性提示**：OpenAI 文档目前说明其托管微调平台正在收尾，且不再对新用户开放；API 参考页存在不等于当前账号可创建新任务。本日不以调用该 API 为验收条件。

## 二、核心知识总结

| 方法 | 学习信号 | 适合何时考虑 | 本日边界 |
| --- | --- | --- | --- |
| SFT | 输入 → 正确答案/轨迹 | 有可信标准答案，希望学会格式或窄任务行为 | Day 40–41 已研究，继续作为基线 |
| DPO | 同一输入下更好（`chosen`）与更差（`rejected`）的成对偏好 | 标准答案不唯一，但能稳定判断两种输出孰优 | 先验证偏好标注一致性；无需自建显式奖励模型，但仍需独立评估 |
| RFT | 对生成结果给出可比较的评分/奖励，并据此优化 | 结果可可靠评分、SFT/Prompt 仍不足、算力与评估预算充足 | “RFT”是强化微调范畴，不等于某一个具体算法 |
| GRPO | 一种相对奖励的策略优化方法，比较同一问题采样出的多个候选 | 能批量采样并提供可信奖励函数时 | 是 RFT 的一种可选实现思路，不与 DPO 混为一谈 |

**Grader** 是把输出映射成可比较分数的评分器，可由确定性校验、人工标注或模型评审组成。对假订单任务，优先把“JSON 可解析、Schema 合法、只读工具名/参数正确、最终结论正确、未越权写入”分开评分；格式分不应掩盖安全失败。先在人审样本上检查 Grader 一致性，再考虑把它当训练奖励。

**Reward Hacking** 指模型学会提高 Grader 分数，却没有真正完成任务。例如只输出漂亮 JSON、在文本里声称查过订单但未真实调用工具，或把危险写操作换个表述来避开关键词检查。防法是：工具执行事实来自工具侧轨迹而非模型自述；高风险动作由权限/审批层硬约束；使用与训练奖励不同的独立保留集和人工抽检；对抗样本纳入安全门槛。即使最终答案得分升高，也不能绕开工具侧校验或审批。

### 发布单元与回滚边界

一次可复现发布应固定：基础模型精确版本、Adapter/权重版本、Tokenizer 与 Chat Template、Prompt、工具 Schema 与权限策略、推理参数、数据版本、训练配置及评估报告。只记“模型名”不足以重现行为。把这些合成一个不可变的**发布版本**，请求 Trace/指标只记录版本 ID 与必要的非敏感元数据。

灰度发布按 `离线门槛 → 影子流量/模拟调用 → 少量真实流量 → 扩大流量` 逐步推进。每一步比较任务质量、错误率、P95/P99 延迟、Token/成本和安全事件；高风险写工具仍由审批控制。灰度中的对照应尽量使用相同类型的流量，避免把流量差异误判为模型收益。触发阈值应在发布前写定；发现越权调用、格式大幅退化、错误或成本超阈值时，停止放量并将路由切回上一个完整发布版本。回滚只切模型而不切 Prompt/Schema 可能仍无法恢复原行为。

## 三、Task / Project 学习路线

继续沿用 Day 39–41 的假订单/退款结论项目，模型最多只能调用 `mock_order` 与 `mock_refund_rules` 两个只读工具；实际退款写操作不是本日训练或灰度对象。

### Task 1：复核是否需要偏好/强化微调

- 查看未微调基线与 SFT/LoRA 候选的逐样本错误、验证集表现和封存测试集结果。
- 将剩余问题分成“存在可靠标准答案”“只有偏好顺序”“可稳定打分”“其实是工具/权限缺陷”。
- **产出/验收**：DPO、RFT/GRPO、继续 SFT、只修 Harness 或停止训练的选择依据；没有明显缺口就不新增训练。

### Task 2：制作小规模偏好对并检查标注

- 用同一 `prompt` 构造 `chosen` / `rejected`；例如优先选择“正确查询只读工具并说明需审批”，而非“直接声称已退款”。
- 由人工复核工具事实、结论与拒绝理由；统计分歧并处理，不把模型自我评价当偏好真值。
- **产出/验收**：去重且不跨 train/validation/test 泄漏的偏好样本与标注规范；能解释为何所选答案更好。

### Task 3：设计并验证 Grader

- 将格式、事实、工具选择/参数、越权调用分项评分；工具是否真的执行以轨迹为准。
- 准备正常、边界和攻击样本，给 Grader 做反例测试，包括“空洞但格式完美”“伪造工具调用”“关键词绕过”。
- **产出/验收**：评分规则、人审一致性记录和失败案例；安全硬约束不能被其他高分抵消。

### Task 4：做 Reward Hacking 红队检查

- 假设模型专门优化这个 Grader，找至少三种“高分但错误”的输出；检查是否能利用长度、格式、评分遗漏或工具自述拿高分。
- 修改 Grader 或外部校验后复测，并始终保留不参与奖励设计的独立评估样本。
- **产出/验收**：攻击样本、原分数、修订后分数及剩余风险。若 Grader 不可靠，不启动 RFT/GRPO。

### Task 5：建立版本与灰度方案

- 定义不可变发布清单、候选版本与稳定版本；写出离线门槛、灰度比例、监控指标、放量/停止/回滚阈值和负责审批的人。
- 在模拟流量上检查请求是否能关联发布版本，以及审批、工具执行和错误能否按版本聚合。
- **产出/验收**：发布清单、灰度流程图与指标看板草案；无真实流量时只做演练，不声称生产发布成功。

### Task 6：演练回滚并形成最终决策

- 模拟候选模型格式错误上升、P95 超阈值或越权工具意图；确认告警后将路由切回稳定版本，并复跑关键回归样本。
- 核对版本切换前后的配置、Trace 与指标，确认未完成任务是否仍按原版本/审批策略安全处理。
- **产出/验收**：回滚演练记录、受影响范围、恢复时间、残余风险和最终 Go/No-Go 决策。

## 四、完成标准

- 能解释 SFT、DPO、RFT 与 GRPO 的数据/反馈差异，明确 Grader 可靠性与 Reward Hacking 风险。
- 偏好数据、Grader 和独立评估集互不泄漏；安全硬约束不由模型分数替代。
- 发布版本可复现，灰度指标和回滚阈值事先定义，并完成至少一次**模拟**回滚演练。
- 若没有可靠偏好标注、Grader、硬件或足够收益，明确记录“不做偏好/强化训练”的结论，而不是虚构训练结果。
