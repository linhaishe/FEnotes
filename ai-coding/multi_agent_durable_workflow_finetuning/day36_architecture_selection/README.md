# Day 36：Agent 架构选型

本日目标：对**同一任务**比较固定 Workflow、Single-Agent、Multi-Agent，依据结果选择满足要求且最简单的方案，并留下可复查的基线数据。本目录先记录学习大纲与实验设计，尚未实现 Demo。

主要阅读：[Anthropic — Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)。

## 一、先弄清三个选项

| 方案 | 谁决定下一步 | 更适合什么任务 | 主要代价或风险 |
| --- | --- | --- | --- |
| 固定 Workflow | 代码预先规定步骤、分支和校验 | 路径明确、结果需要可预测或易审计 | 对未预见的任务变化不够灵活 |
| Single-Agent | 一个 Agent 根据反馈选择工具和下一步 | 步骤难以完全预先枚举，需要适度自主性 | 工具选择可能出错，调用次数与成本更不稳定 |
| Multi-Agent | 一个协调者委派给多个专长 Agent，或在受控条件下并行协作 | 子任务边界清晰，单 Agent 基线不足，拆分收益可测 | 协调、上下文传递、错误传播与成本更复杂 |

**注意区分原文与本日扩展**：原文首先区分“预定义代码路径的 Workflow”和“模型动态控制过程的 Agent”，并介绍 routing、parallelization、orchestrator-workers 等模式；本日把“单 Agent 还是多个 Agent 协作”作为第二个选型维度，形成上表的三方案比较。并行不等于 Multi-Agent：固定 Workflow 也可以并行执行独立步骤。原文建议先使用最简单的可行方案，只有质量提升能抵消额外延迟与成本时才增加复杂度。

## 二、阅读大纲

1. **Workflow 与 Agent 的边界**：谁控制流程？步骤是否能预先确定？失败后由代码还是模型决定下一步？
2. **常见 Workflow 模式**：prompt chaining、routing、parallelization、evaluator-optimizer。为每种模式找一个适用例子，说明其固定部分在哪里。
3. **自主 Agent 的适用边界**：开放任务为什么可能需要动态规划与工具反馈？为什么必须限制迭代次数、工具权限和预算？
4. **Orchestrator-workers 与 Multi-Agent**：只有子任务无法提前固定、或专业分工确实改善结果时，才考虑协调者委派；明确如何合并结果与处理子任务失败。
5. **选型原则**：先建立简单基线，再依据相同评估集比较质量、延迟、Token/成本与失败情况；复杂方案不能仅凭“更像 Agent”胜出。

## 三、同题对照实验

建议使用一个不产生真实外部副作用的任务，例如“根据订单记录和退款规则，判断是否可退款并生成解释”。准备正常请求、缺失字段、规则冲突、需人工审批及恶意文档指令等固定样本；订单和规则都使用假数据。

保持任务说明、输入样本、可用工具、模型版本与价格口径一致，分别实现：

1. **Workflow 基线**：代码按固定顺序读取订单、读取规则、校验条件并生成回答；审批条件由代码判断。
2. **Single-Agent**：一个 Agent 自主选择只读工具和生成步骤；写操作仍经相同权限校验与审批。
3. **Multi-Agent**：在确有独立子任务时，由协调者把“订单事实提取”和“规则核对”交给不同子 Agent，最后统一验证和汇总；限制委派深度、并发和总预算。不要让多个 Agent 共用可写工具权限。

先跑 Workflow 和 Single-Agent。只有评估显示它们存在具体缺口，再实现 Multi-Agent 对照；否则记录“无需 Multi-Agent”也是合格的选型结论。

## 四、基线指标与记录方式

对每个方案使用**同一批样本**，逐任务保存 `case_id`、预期结果、实际结果、是否正确、调用次数、工具错误、总耗时、输入/输出 Token 与估算成本。汇总时至少比较：

| 指标 | 计算或判定方式 | 为什么要看 |
| --- | --- | --- |
| 任务成功率 | 正确且满足业务与安全约束的任务数 ÷ 总任务数 | 避免只看回答是否流畅 |
| 工具选择/参数正确率 | 工具、参数及权限均正确的任务数 ÷ 需调用工具的任务数 | 识别自主决策的代价 |
| 安全违规数 | 未经审批执行写操作、越权访问等次数 | 安全约束不能用速度或低成本抵消 |
| 延迟 | 逐任务耗时；样本足够时再比较 P50/P95 | 观察串行、并行和协调开销 |
| Token 与成本 | 记录实际用量；按相同价格口径汇总每任务成本 | 比较额外规划和委派的费用 |
| 失败与恢复 | 超时、工具异常、子任务失败后的最终结果 | 比较复杂架构是否更脆弱 |

先写清楚必须达到的质量和安全门槛，再从满足门槛的方案中选择实现与运维成本最低的一个；若指标接近，优先较简单的方案。不要用少量样本宣称 P95 有统计意义，也不要把不同模型或不同工具权限下的数据直接比较。

## 五、完成产物

- 一份固定样本及预期结果，覆盖正常、边界和攻击输入。
- Workflow 与 Single-Agent 的基线记录；若尝试 Multi-Agent，还需相同口径的对照数据。
- 一页选型结论：任务特征、候选方案、评估数据、选定方案、没有选择其余方案的原因，以及仍需验证的风险。

自检：如果任务步骤完全可预先写出，为什么要让模型控制流程？如果两个子任务可以并行，是否必须引入两个 Agent？增加 Agent 后，什么指标证明这不是无收益的复杂化？
